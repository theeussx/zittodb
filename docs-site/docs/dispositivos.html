01

Uma camada visual para ferramentas que você já conhece

O ZittoDB não reimplementa o protocolo ADB. Ele valida a intenção, monta argumentos explícitos e deixa adb, scrcpy e fastboot fazerem o trabalho. Assim, a interface fica mais clara sem esconder o que realmente será executado.

02

Dependências do sistema

O ZittoDB usa as ferramentas oficiais instaladas no seu Linux:

sudo apt update
sudo apt install adb fastboot
# scrcpy é opcional, para espelhamento e gravação
sudo apt install scrcpy
  • ADB é necessário para detectar e controlar aparelhos Android.
  • scrcpy 3.2+ é necessário para o espelhamento compatível com Android 15.
  • fastboot só é necessário para a aba Fastboot.
!
scrcpy no Ubuntu

O pacote da distribuição pode estar desatualizado. Para Android 15, prefira o release oficial do scrcpy.

Primeiros passos

Em poucos minutos você conecta um aparelho, confirma a autorização e chega às ferramentas principais.

01

Ative a depuração USB

No Android, habilite as opções de desenvolvedor e a Depuração USB. Conecte o cabo e desbloqueie a tela.

02

Confirme a chave RSA

Na primeira conexão, aceite a janela de autorização no aparelho. O ZittoDB nunca tenta burlar essa etapa.

03

Selecione o dispositivo

Abra Dispositivos, escolha o serial conectado e explore as abas de visão geral, aplicativos, arquivos, shell e logs.

04

Se o aparelho não aparecer

adb devices -l
EstadoSignificadoO que fazer
deviceConectado e autorizadoPronto para usar
unauthorizedA chave RSA ainda não foi aceitaDesbloqueie e aceite no aparelho
offlineA conexão não respondeuReconecte o cabo ou reinicie o ADB
GUIA DO USUÁRIO

Dispositivos

O centro do ZittoDB é o painel do dispositivo. Cada ação é direcionada ao serial selecionado — nunca a um aparelho escolhido implicitamente.

A

USB, Wi-Fi e emuladores

A lista identifica o tipo de conexão e exibe estados como conectado, offline, não autorizado e recovery.

B

Conexão por Wi-Fi

Use a ação de conectar com host e porta. Para o modo navegador, você também pode usar adb connect IP:PORTA no terminal.

C

Informações sob demanda

Consulte propriedades, bateria, armazenamento, rede, memória e patch de segurança sem coleta contínua.

GUIA DO USUÁRIO

Segurança

A interface mostra o que vai acontecer, mas a decisão final de execução pertence ao backend Rust.

◇
O frontend exibe dados. O backend executa operações.

Essa separação evita que uma entrada da interface vire um comando arbitrário.

01

Allowlist em Rust

As operações são tipos explícitos e viram vetores de argumentos validados. Não existe sh -c para montar comandos.

02

Confirmações digitadas

Ações destrutivas pedem palavras exatas como APAGAR, REMOVER, REINICIAR ou FLASHAR.

03

Serial explícito

Cada operação recebe o serial do dispositivo selecionado, evitando o alvo implícito “qualquer dispositivo”.

04

Sem telemetria

Configurações, auditoria, histórico e logs ficam no filesystem local. A única consulta externa é a metadata pública de releases.

05

Onde os dados ficam

~/.config/app.zittodb.desktop/
├── settings.json
└── audit.jsonl

~/.local/share/app.zittodb.desktop/
└── logs/zittodb.log

Leia o modelo de ameaças completo para detalhes de armazenamento, processos e limites.

Arquitetura

A arquitetura é desktop-first, local-first e orientada a fronteiras claras.

React
UI + Zustand
→
Bridge
Tauri · local · mock
→
Rust
validação + processos
→
Ferramentas
adb · scrcpy · fastboot
02

Princípios

  1. Leve primeiro. Sem Electron e sem ADB embutido.
  2. Backend dono da execução. A UI descreve o quê; o Rust controla como.
  3. Operações tipadas. Ações novas entram na allowlist e ganham testes.
  4. Concorrência por serial. Operações conflitantes no mesmo aparelho são serializadas.

Veja o documento de arquitetura para o contrato Bridge, timeouts, eventos e storage.
